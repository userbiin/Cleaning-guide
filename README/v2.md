# Organization Object Detector — 최종 구현 명세 (v2)

> 어질러진 공간 사진 → **Detector**(박스) → **Florence-2 describe**(속성) → **Category 매핑** →
> **LLM 정리 판단**(discard / relocate / keep + 가이드) → **iOS 앱 렌더**.
> 핵심 가설: **describe 속성 정보를 추가하면 LLM의 정리 판단 정확도가 유의미하게 향상된다.**

이 문서는 대화로 확정한 구조를 Claude Code가 그대로 구현하기 위한 명세서다. 이 문서만으로 자족적이다.

---

## 0. MVP 라인 (가장 먼저 읽을 것)

**무리하게 다 하지 말고 MVP 코어부터 끝낸다.**

| 구분 | 범위 |
|---|---|
| **MVP 코어 (필수)** | 추론 파이프라인 1개 경로(YOLO-World + Florence-2) · describe **ON/OFF A/B 실험** · 단계별 실패 귀속 · describe 신뢰도 감사 · **iOS 시연 앱** |
| **스트레치 (시간 남으면)** | 다중 detector 비교(YOLOE, Florence-DRC) · HomeObjects-3K/LVIS **fine-tuning** · SAM 2 segmentation · 선호도 평가 정식 실험 |

> 우선순위: **MVP 코어 → 스트레치**. fine-tuning·다중모델 비교는 baseline A/B가 돌아간 *뒤*에 붙인다.

## 1. 확정 시스템 구조

### 1.1 추론 파이프라인 (run-time)
```text
[iOS 사진] → OpenCV 전처리 → Detector 슬롯 → Describe 슬롯(Florence-2)
          → Attribute 파싱 → Category 매핑(6종) → LLM 판단 → [iOS 렌더]
```
- **Detector 슬롯 (교체 가능)**: YOLO-World(기본) / YOLOE / Florence-DRC. MVP는 YOLO-World 고정.
- **Describe 슬롯**: Florence-2 (고정). label + attribute 서술 생성.
- 두 슬롯은 **역할이 다르다**. detector=박스 찾기, describe=속성 서술. 비교 실험은 detector 슬롯에 한정.

### 1.2 평가 파이프라인 (`eval/` 디렉터리로 완전 분리)
```text
Detector 단계  → A. 소형 object Recall / FP rate
Describe 단계  → describe 신뢰도 감사 (표본 + CI)
LLM output 단계→ B. cost-weighted decision acc + category acc
                 (+ 선호도 평가: blind OFF vs ON)
        ↓
단계별 실패 귀속 (detect / describe / category / llm)
        ↓
개선 루프 → detector targeted fine-tune (HomeObjects-3K/LVIS)
          → describe 슬롯: 프롬프트 / state-signal 키워드 재교정 (※ VLM 재학습 아님)
```
> **지표는 측정 지점이 다르다.** A는 detector에서, B는 LLM output에서 측정한다. end-to-end 수치만 보면 어디서 실패했는지 알 수 없으므로 **단계별로 귀속**한다.

## 2. Decision Taxonomy (프롬프트 출력 = 라벨링 정답, 동일 기준)

세 값으로 고정. 이 기준이 **LLM 출력 형식**이자 **사람 라벨링의 정답 정의**다.

- `discard` (버릴 것): 재사용 의도 없는 빈 용기·포장지·다 쓴 소모품
- `relocate` (옮길 것): 유효하지만 현재 위치가 부적절한 물건
- `keep` (제자리): 현재 위치가 적절한/상시 사용 물건

경계 규칙(라벨링 가이드라인에 명문화): 반쯤 남은 음료 = relocate(세척) / 빈 캔 = discard / 모호 시 keep.
라벨러 **2인 이상**이 이 기준으로 라벨링 → **Cohen's kappa**로 일치도 측정(라벨 자체 신뢰도 확보).

## 3. LLM 프롬프트 ON/OFF 스펙 (A/B의 처치)

**공정성 원칙: OFF와 ON의 유일한 차이는 `description` + `state` 두 줄.** instruction·출력형식·객체리스트 구조·모델·temperature는 100% 동일.

공통 instruction (양쪽 동일):
```
너는 실내 정리 컨설턴트다. 아래 탐지된 물건 각각에 대해
discard / relocate / keep 중 하나를 판정하라.
판정 기준:
- discard: 재사용 의도 없는 빈 용기·포장지·소모품
- relocate: 유효하지만 현재 위치가 부적절한 물건
- keep: 현재 위치가 적절한 물건
확신이 낮으면 keep으로 둔다.
```

객체 리스트 — **OFF (control)**:
```
[쓰레기/기타]
- bottle (conf 0.71) ×1
```
객체 리스트 — **ON (treatment)** (두 줄만 추가):
```
[쓰레기/기타]
- bottle (conf 0.71) ×1
    · description: "a crumpled empty plastic bottle"
    · state: trash_signal
```

공통 출력 계약 (양쪽 동일, 머신 비교용 JSON 강제):
```json
{
  "decisions": [ {"object_id": 0, "label": "bottle", "decision": "discard"} ],
  "guide": { "priority_top3": ["..."], "five_min_routine": ["..."], "by_category": {} }
}
```

## 4. 모델 전략 — "택일"이 아니라 "순서"

1. **선택 단계 (학습 0)**: dev 50장에 여러 detector(YOLO-World/YOLOE/Florence-DRC)를 **zero-shot 추론**만 돌려 Recall 비교 → **base detector 1개 선정**.
2. **개선 단계**: 선정된 base의 **실패 클래스만** 골라 targeted fine-tune.
   - **HomeObjects-3K** (폰 사진과 가장 가까움) → 1순위
   - **LVIS** (가위·리모컨·립밤 등 long-tail/소형) → A 지표 개선용, 2순위
   - OCID는 RGB-D 도메인 갭으로 후순위/제외
   - 데이터셋은 "다" 말고 **실패 유형에 맞춰 1~2개만**.

## 5. 평가 설계 (`eval/`)

### 5.1 데이터 분리 (수치 고정)
| 셋 | 출처 | 크기 | 용도 |
|---|---|---|---|
| fine-tune train/val | HomeObjects-3K / LVIS (공개) | 자체 split | detector fine-tune (사용자 사진과 별개 우주) |
| **dev** | 직접 수집 | **50장** | 모델 선정 · 프롬프트/threshold/keyword 튜닝 |
| **test** | 직접 수집 | **100장 (freeze)** | 최종 A/B 단 1회 |
- 수집 목표 총 **150장** (최소 50 / 스트레치 200). **dev ∩ test = ∅.**
- **분석 단위 = per-object 결정** (test ≈ 800~1200개) → 통계 검정력 확보.
- 50장만 가능하면 dev 15 / test 35 + 5-fold CV(선정용) + 넓은 CI로 보고.

### 5.2 지표 정의
- **A. Detection (detector 단계)**: Small Object Recall, 전체 Recall, FP rate. GT bbox 대비.
- **B. LLM 판단 (output 단계)**:
  - plain decision accuracy
  - **cost-weighted accuracy**: 오류 비용이 다르다. `discard→keep`(쓰레기 방치)에 페널티 가중. 아래 cost matrix 예시:
    ```text
              pred:discard  pred:relocate  pred:keep
    gt:discard      0            2             3      
    gt:relocate     3            0             1
    gt:keep         4            1             0      ← 멀쩡한 물건을 discard하는게 최악
    ```
  - **discard recall** 별도 보고 ("쓰레기 안 놓침" = 상업 가치 직결)
  - **category accuracy** (매핑 단계)
- **선호도 평가 (생성물, 정답 없는 부분)**: describe OFF/ON 가이드를 **가린 채** 평가자가 pairwise 선택. "describe ON 선호율" 보고.

### 5.3 단계별 실패 귀속 (`eval/attribution.py`)
객체마다 trace 레코드를 남기고, **cascade 로직**으로 실패 단계를 귀속한다.
```python
# trace 레코드 (이미지×객체 단위)
{
  "image_id": "test_012", "object_id": 3,
  "gt_bbox": [...], "gt_decision": "discard",
  "detected": true, "pred_bbox": [...],
  "describe": "a crumpled empty bottle",
  "describe_correct": true,        # 감사 표본만 채움, 그 외 null
  "pred_category": "trash_or_misc", "category_correct": true,
  "pred_decision": "discard", "decision_correct": true,
  "failure_stage": null
}

# 귀속 로직 (위에서부터 cascade)
def attribute_failure(t):
    if not t["detected"]:                 return "detection"
    if t["describe_correct"] is False:     return "describe"
    if t["category_correct"] is False:     return "category"
    if t["decision_correct"] is False:     return "llm"
    return None
```
출력: 단계별 실패 비율 분포 → "최종 오류의 N%는 detection 누락에서 발생" 같은 진단 → **어디를 개선할지** 결정.

### 5.4 Describe 신뢰도 감사 (`eval/audit.py`)
- **감사 대상**: Florence-2가 **평가용 사진**에 생성한 describe 출력만(공개 학습셋 아님). ≈ 800~1000개로 바운드.
- **전수 아님, 표본 추출**:
  - 표본 수 **100~150** (95% CI, 오차 ±10%면 ~96, ±7%면 ~196).
  - **층화**: `state_signal`별로 나눠 뽑되 **결정을 뒤집는 서술**(예: "empty"→discard)을 오버샘플.
  - **선검수(선택)**: VLM/LLM으로 describe↔crop 불일치 의심 건 플래그 → 사람은 플래그 + 무작위 대조군만 확인.
- **보고**: "describe accuracy = X% (95% CI [a,b])", signal type별 분해.

### 5.5 통계 (`eval/stats.py`)
- describe ON vs OFF: per-object 결정 정확도에 **paired test** + **Cohen's d(effect size)** + **95% CI**.
- 라벨 신뢰도: 라벨러 간 **Cohen's kappa**.
- "유의미한 향상"은 p값 단독이 아니라 **effect size + CI**로 주장.

## 7. 백엔드 (FastAPI)

### 7.1 Cold start 대응 (필수)
Florence-2는 첫 요청 로딩이 크다. **lifespan 이벤트로 서버 기동 시 모델 사전 로드.**
```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.detector = Detector("yolov8s-world.pt")      # 사전 로드
    app.state.describer = Florence2Describer()              # 사전 로드
    yield
app = FastAPI(lifespan=lifespan)
```

### 7.2 API 계약 `POST /analyze` (multipart/form-data)
- 입력: `image`(jpg/png/**heic**), `describe`(bool, 기본 true), `detector`(기본 "yolo-world")
- 응답: `processed_image_size:[w,h]` **포함**(iOS bbox 스케일링용), `objects[]`(label/description/state/category/decision/confidence/bbox), `guide{}`, `annotated_image_url`, `latency_ms`

## 10. Florence-2 describe 구현 메모
- **Proposed-B (MVP 기본)**: `<DENSE_REGION_CAPTION>` → 박스+서술 1-pass. region token 변환 불필요.
- **Proposed-A (스트레치)**: YOLO 박스를 **crop해서 캡션** → token 변환 회피.
  ```python
  def describe_region(self, image, bbox, pad=0.08):
      x1,y1,x2,y2 = bbox; w,h = image.size; bw,bh = x2-x1, y2-y1
      crop = image.crop((max(0,int(x1-bw*pad)), max(0,int(y1-bh*pad)),
                         min(w,int(x2+bw*pad)), min(h,int(y2+bh*pad))))
      return self._run(crop, "<MORE_DETAILED_CAPTION>")
  ```
  트레이드오프: crop은 주변 scene 맥락 손실(객체 상태 서술엔 충분). 전체 맥락 필요 시 location-token 방식은 모델 카드 검증 후.

## 12. Claude Code 즉시 작업
1. 6장 디렉터리 스캐폴딩 생성 (`eval/` 분리 포함).
2. v1 `baseline.py`의 `CATEGORY_MAP`/`classify_item`/프롬프트 빌더를 `pipeline/`으로 이식, detector는 **박스 dict만 반환**하도록 리팩터링.
3. `app/main.py` + `schemas.py`: lifespan 사전로드 + `/analyze` (describe OFF부터 통과), 응답에 `processed_image_size` 포함.
4. `models/describer.py`: Florence-2 `<DENSE_REGION_CAPTION>` 동작 확인.
5. `pipeline/orchestrator.py` + `attributes.py` + `pipeline/llm.py`: describe flag 분기, 3장 ON/OFF 프롬프트, JSON decision 출력.
6. `eval/`: `metrics.py`(cost-weighted), `attribution.py`(cascade), `audit.py`(층화 표본), `stats.py`(Cohen's d/CI/kappa), `run_ab.py`(ON/OFF).
7. `eval/labeling_guide.md`: 2장 taxonomy + 경계 규칙.
8. `ios/`: SwiftUI 업로드 + bbox 스케일링 + 에러처리 최소 앱.
9. `requirements.txt` (pillow-heif, scipy, scikit-learn 포함).

> 구현 순서: **describe OFF 경로 먼저 통과 → describe ON 얹기 → eval A/B**. OFF가 대조군이므로 절대 건너뛰지 말 것.

## 13. 개발 환경 & 디바이스 배치 (Mac M4 24GB ↔ 4090, Tailscale 연결됨)

**환경**
- 개발 머신: MacBook Air **M4 / 통합메모리 24GB / SSD 1TB** (Apple Silicon → PyTorch `mps`, **CUDA 없음**)
- 실행/학습 머신: **RTX 4090** (CUDA, 24GB VRAM) — **Tailscale로 맥북에 원격 연결 완료**

**기준 한 줄**: 코드 작성은 전부 맥북, **무거운 모델 대량 추론·모든 fine-tuning은 4090.** 갈리는 건 단계가 아니라 "프로세스가 어디서 실행되냐"다.

### 13.1 24GB M4에서 가능한 범위
- YOLO-World-small: `mps`로 쾌적.
- Florence-2-**base**: 쾌적 / **large**: 느리지만 **smoke test(1~몇 장) 가능**(24GB라 로드됨).
- 대량 추론(test 100장 × ON/OFF)·fine-tuning: **4090.** (맥에서 돌리면 비현실적으로 느림)
- 맥 추론 시: Florence-2는 `attn_implementation="sdpa"`(또는 `"eager"`)로 로드, `mps` float16 불안정하면 float32로.

### 13.3 P5: 예측 생성과 채점 분리 (핵심 패턴)
모델은 **4090에서 1회만** 돌려 trace를 저장하고, **채점·통계·cost matrix 튜닝은 맥에서 무한 반복**한다. → cost 가중치를 바꿔도 GPU 재실행 불필요.
```text
[4090] eval/run_ab.py → outputs/traces/*.json   (Florence-2 대량 추론, 1회)
            │  rsync (Tailscale)
            ▼
[맥북] eval/metrics.py · attribution.py · stats.py   (numpy/scipy, 반복)
```

### 13.4 Tailscale 연결 (이미 구성됨)
- 동기화: 맥에서 `git push` → 4090 `git pull` 후 실행. 또는 **VS Code Remote-SSH로 4090 파일 직접 편집**(Tailscale IP로 SSH).
- 백엔드 접근: iOS 앱·맥은 **4090의 Tailscale IP(`100.x.x.x`)** 로 `/analyze` 호출. (별도 포트포워딩/ngrok 불필요)
- trace 복사: `rsync -avz <4090-tailscale-ip>:~/organize-detector/outputs/traces ./outputs/`
- iOS 데모: `Info.plist` ATS에 **4090 Tailscale IP 예외** 추가(데모 한정 평문 HTTP 허용).
